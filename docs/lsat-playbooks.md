# LSAT Question-Type Playbooks

A **playbook** is how one LSAT question type is recognised and solved: the stem phrasing that gives it away, the task in one line, the strategies that apply, the method as steps, and the traps planted in its wrong answers. Playbooks are the answer key and the teaching content for the lab's **Diagnose first** exercise, which asks a learner to name a question's type and strategy before the answer choices appear. Introduced by [specs/053-lsat-question-diagnosis](../specs/053-lsat-question-diagnosis/spec.md).

Playbooks sit between two existing layers. A solve guide ([docs/lsat-solve-guides.md](lsat-solve-guides.md)) walks one question; a library article ([docs/lsat-library.md](lsat-library.md)) explains a family in prose. A playbook is the structured pattern for one archetype, keyed to the factory taxonomy, and it is data rather than prose so the exercise can mark against it.

## How a question gets its type

The exam signals type through the question sentence, so that is what the classifier reads: the last paragraph of the stem, matched case-insensitively against each same-section playbook's `cue_patterns`. When several match, the lowest `priority` wins, then the largest concept overlap with the archetype. Two rules make the flaw and inference families resolve: a playbook with `requires_concepts_any` only counts when the item carries one of those concepts, so `lr-causal-flaw` beats `lr-flaw-general` exactly when the item is tagged `causation-vs-correlation`; and specific types carry a lower priority than their general sibling, so "similar in its flawed reasoning" is a parallel flaw before it is parallel reasoning.

Logic Games needs one more rule. The registry mixes task archetypes (acceptability, local conditional, could-be-true-except, max/min, numeric distribution, rule substitution) with game-type archetypes (grouping, hybrid, in/out selection). Task cues win; a global must-be-true with no new condition falls to the game-type archetype its concepts name, and to `lg-must-be-true` in a plain sequencing game.

A stored `archetype` stamp always wins over the classifier. With no cue hit at all the item falls back to the unique archetype whose primary concept it carries (the coverage census's own contract), and to "unclassifiable" rather than a guess.

## Re-stamping the bank

```bash
# Report: is every item stamped? Non-zero exit if not.
make manage CMD='lsat_archetype_backfill --check'

# Stamp only items that have no archetype yet.
make manage CMD='lsat_archetype_backfill'

# Re-derive every stamp from the stem and rewrite any that disagree.
make manage CMD='lsat_archetype_backfill --force'

# Then refresh the static bundle, which carries the stamps.
make lsat-export
```

`test_every_bank_item_is_stamped_and_the_stem_agrees` clears each stamp and re-runs the classifier; a new item that arrives unstamped, or a stamp the stem does not support, fails the suite. Review the resulting bank diff in the pull request; that review is the HITL gate for bank content.

## Adding or editing a playbook

Every question archetype in `taxonomy.py` must have exactly one playbook, and loading fails loudly on a missing one or a dangling `strategy_ids`, `trap_ids` or `confused_with` reference. To add a type, add the archetype to the registry first, then its playbook entry. Keep `cues` as the phrasings a learner will see and `cue_patterns` as the regexes the classifier runs; the learner never sees the patterns. Put the traps the type is *built around* in `trap_ids` (the shared glossary is where a trap is defined once), and list in `confused_with` the types learners actually swap it with, because those are dealt first as distractors. Nothing in the catalog is generated by a model; `source` is `original (CC0)`.

## The exercise

`GET /api/lsat/questions/<id>/diagnose` deals five same-section type options (the key plus its look-alikes, then the rest of the section) and four strategies (always including the key's primary), shuffled by a seed that defaults to the question id. Nothing in the payload marks the key. `POST` with `{archetype_id, strategy_id?}` returns the verdicts, `family_correct` as partial credit (right family, wrong sub-type), the cue quoted from this stem, and the playbook. Every call writes an `lsat_diagnose` audit event; a signed-in learner also gets an `LsatDiagnosisAttempt` row, which is a sibling of `LsatAttempt` so recognition practice never enters the answer-accuracy denominator or the review queue. The `diagnosis` block on `/api/lsat/stats` reports type, family and strategy accuracy, the weakest types, and the confusion pairs.

## Contrast variations (spec 054)

A **contrast variation** keeps a question's stimulus verbatim and re-asks it as a different archetype, with a `contrast_note` on where the key moved and why. A root plus its variations is a **contrast set**; the post-grade contrast panel shows the graded item's note and offers the siblings, and `/lsat?question=<id>` opens the drill on one. The service is `backend/law_ai/lsat/services/contrast.py`; the endpoints are `GET /api/lsat/questions/<id>/contrast` (notes only with `?spoilers=1`) and `POST /api/lsat/questions/<id>/variations`.

Variations are drafted by `LSATContrastAuthor` through the review loop in `backend/law_ai/lsat/factory/revise.py`: the deterministic gates in `validate_variation` (stimulus preserved, stem classifies as the target type, key not the root's, traps known) and `LSATDraftJudge` object, the objections go back to the author as a critique (a `fail`, a disagreeing blind key, or a `flag` with concrete issues while rounds remain; a malformed answer counts as an objection too), and after the cap the last draft is filed anyway, flagged, with every round's history on `meta.revisions`. Approval promotes it like any question and carries `variation_of`, `contrast_note` and the target `archetype` into the bank.

```bash
make lsat-contrast-sweep ARGS='--source lr-002 --target lr-evaluate-argument'
make lsat-contrast-sweep ARGS='--limit 3 --dry-run'
```

The stamps themselves are checked by `LSATTypeReviewer`, which reads each item blind against the section's type menu. `make lsat-type-review ARGS='--section LR --limit 10'` files each disagreement as a `typecheck` proposal; on the Authoring tab, "Restamp as X" rewrites the item's `archetype` and "Keep current stamp" closes the row unchanged.

## Judge-driven rewrites and the Fable final review (spec 054)

`make lsat-question-review ARGS='--section LR --limit 10'` asks `LSATDraftJudge` to attack each bank item as it stands. A clean verdict is cached and nothing is filed. An objection sends the item to `LSATQuestionEditor`, which makes the minimal rewrite that answers it; `validate_rewrite` (`backend/law_ai/lsat/services/rewrite.py`) refuses a type change and, for a contrast-set member, any change to the shared stimulus; the judge attacks the rewrite; and the loop repeats up to the cap. Every accepted draft — variations and rewrites alike — then gets one independent verdict from the final-review model, Fable by default (`LSAT_FINAL_REVIEW_MODEL`, both Claude tiers pinned); a `fail` there files the draft unaccepted, a `flag` is a reservation shown on the card. On the Authoring tab a rewrite card shows the judge's original objections, the change summary, both versions, the revision history and the final-review badge; "Approve → replace lr-NNN" rewrites the item in place with an editorial review record, "Keep original" closes the row. `POST /api/lsat/questions/<id>/review` runs the same loop for one item.


## Static edition (#126)

As of schema v4, `make lsat-export` ships learner-facing playbooks into `lsat-static/content.json` (strategies, traps, and `public_playbook_view` items — **without** `cue_patterns`). The offline site uses stamped `Question.archetype` for lookup; Diagnose-first remains lab-only.
